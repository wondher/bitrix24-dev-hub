# Plano: Tool MCP `b24_call` — chamadas live ao Bitrix24 via endpoint configurado localmente

## Objetivo

Adicionar uma 10ª tool MCP, `b24_call`, estilo Postman, que faz chamadas HTTP reais a um endpoint Bitrix24 (webhook inbound) configurado num arquivo **gitignored**. A IA fornece só `method` + `params`; o token fica embutido na URL e nunca é exposto. A resposta é pós-processada (paginação detectada, payload truncado) para não estourar o contexto — ideal pra explorar SPAs, stages, campos e montar lógica de processos.

## Decisões (confirmadas com o usuário)

- **Formato do config**: JSON local editável (`.b24.config.json`), com `.b24.config.example.json` versionado.
- **Shape da tool**: genérica + paginação inteligente (uma única tool `b24_call`).
- **Auth**: só webhook inbound nesta v1 (token na URL, sem `auth` separado, sem refresh). OAuth fica p/ depois.

## Arquivos

### Criar

1. **`mcp-server/lib/b24client.js`** — módulo da feature. Funções (todas ESM, sem deps novas):
   - `resolveConfigPath()` — precedência: `B24_CONFIG_PATH` (env) → `<hubRoot>/.b24.config.json` (via `resolveHubRoot({autoBootstrap:false})` de `lib/store.js`, capturando erro → `null`).
   - `loadEndpointConfig({ profile })` — lê/parseia o JSON uma vez por processo (cache em módulo). Normaliza dois formatos aceitos: **flat** (`{baseUrl, userId, webhookToken}`) **ou profiles** (`{profiles:{default:{...}}}` → usa `B24_PROFILE||'default'`). Valida: `baseUrl` começa com `https://`, `userId` numérico, `webhookToken` não-vazio. Retorna `null` se o arquivo não existir (a tool trata como "não configurado"). Lança `Error` legível se o arquivo existir mas for inválido.
   - `buildWebhookUrl(cfg, method)` — `${baseUrl sem barra final}/rest/${userId}/${webhookToken}/${method sem barra inicial}.json`. (Mesmo padrão de `tools/crest/src/crest.php:93`, `sdks/php/.../ApiClient.php:185`, `sdks/python/.../call_method.py:67`.)
   - `callB24Method(cfg, method, params, { start } = {})` — `fetch(POST, JSON body)`, injeta `params.start` se informado, `AbortSignal.timeout(20000)`, headers `Content-Type: application/json`. Em erro HTTP ou `result.error` do Bitrix24, lança `Error` com `{ status, body }` anexados.
   - `formatB24Result(method, result, requestedStart)` — monta texto markdown: `✅ method`, `total`/`next` detectados, payload em bloco ```json truncado em ~20k chars com nota, e instrução `📌 Call again with start=<next>` quando houver próxima página.
   - As funções puras (`buildWebhookUrl`, `formatB24Result`, normalização/validação) são **exportadas** p/ teste.

2. **`.b24.config.example.json`** (na raiz do repo, **tracked**) — documenta o schema:
   ```json

       "default": {

         "userId": "89",
   ```

## Não mexer

- `package.json` — sem nova dependência (native `fetch`), sem mudar `files`/`bin`/`engines`.
- `lib/store.js`, `lib/indexer.js`, `lib/reader.js` — apenas **reutilizo** `resolveHubRoot`.
- Demais SDKs/UI/docs (submódulos) — intocados.

## Segurança

- Token só existe no arquivo local (gitignored); nunca é logado, nunca aparece na resposta da tool.
- Só HTTPS aceito (validado).
- Timeout de 20s p/ evitar travamento.
- Resposta truncada em ~20k chars p/ preservar contexto.
- V1 restrito a webhook inbound (token de escopo limitado, revogável), sem OAuth/refresh.

## Critério de pronto

- `npm test` passa (incluindo novos testes).

- `git status` mostra `.b24.config.json` como **untracked ignorado** (não aparece), e `.b24.config.example.json` como novo arquivo tracked.
- Resposta da tool nunca contém o token.
