Criar uma skill de **referência/roteamento** que ensina o agente a escolher corretamente entre as 10 tools MCP do b24-dev-hub (`b24_call` + 9 `b24hub_*`) para qualquer intenção de desenvolvimento Bitrix24, incluindo convenções de domínio (entidades CRM, SPA, auth, scopes, REST v1/v3).

### Seções
1. **Overview** (2-3 linhas): o que é o hub; divisão canônica — 9 tools `b24hub_*` (leitura local, **offline**) + 1 tool `b24_call` (**live**, faz HTTPS real ao portal).
2. **Regra de ouro**: ler a doc com `b24hub_api_method` **antes** de chamar `b24_call` (a IA fornece só `method`+`params`; o token vem do `.b24.config.json`, nunca exposto).
3. **Fluxograma de decisão** (DOT pequeno, ~10 nós): intenção do usuário → tool. Nó raiz "Sabe o nome exato?" ramifica para as tools especializadas; nó "Não sabe/quer descobrir" → `b24hub_search`/`b24hub_list`; nó "Quer dado real do portal" → `b24_call`.
4. **Quick reference table** (10 linhas): cada tool, 1 linha com intenção-típica + parâmetros-obrigatórios.
5. **Fluxos canônicos** (3-4 receitas curtas, links para references):
   - Projetar um processo SPA (smoke test → lista items → fields → stages)
   - "Como uso o método X?" → ler doc → gerar código
   - Descobrir componente UI → ver props → copiar padrão
   - Reagir a evento → achar evento → achar `event.bind`
6. **Armadilhas** (as 9 mapeadas, formato tabela `Pitfall | Use instead`): ex.: "`b24hub_examples` não cobre Python", "`sdk-services` lista só PHP", "`b24_call` é REST v1 só", "`.b24.config.json` com credencial real no working tree — confirmar gitignore".
7. **Referências cruzadas** (com marcador explícito): "Para detalhes de cada tool: veja `references/mcp-tools-reference.md`. Para convenções Bitrix24 (entidades, SPA, auth, scopes): veja `references/bitrix24-conventions.md`."

## Arquivo 3 — `references/bitrix24-conventions.md` (~1000-1500 palavras)

Domínio Bitrix24 para acertar código de primeira:
1. **Entidades CRM**: lead, deal, contact, company, requisite — quando usar cada, IDs, relacionamentos.
2. **SPA / Smart Processes (crm.item.\*)**: o que são, `entityTypeId` (152 comum para "Processos"), diferença `crm.item.*` (universal) vs `crm.lead.add` (específico).
3. **Auth**: webhook inbound (user-id + token na URL, usado por `b24_call` e CRest) vs OAuth (app público, local app) — quando cada um.
4. **REST v1 vs v3**: `/rest/<uid>/<token>/<method>.json` (v1, o que `b24_call` monta) vs `/rest/api/...` (v3, OpenAPI). Limitação do `b24_call`.
5. **Scopes & permissions**: o que são, onde ver (`docs/rest-api/api-reference/scopes/permissions.md`), como afetam webhook inbound.
6. **Eventos**: `event.bind`/`unbind`, eventos online vs offline, padrão `On<Entity><Action>` (ex.: `OnCrmLeadAdd`).
7. **Batch**: `batch` (universal, até 50 comandos), onde ver exemplos (`b24hub_examples({topic:"batch"})`).
8. **SDK entry points**: PHP `ServiceBuilderFactory`, JS `initializeB24Frame`/`B24Hook`/`B24OAuth`, Python `Client`.

### Sobre o "Iron Law" (TDD p/ skills)
Esta é uma **Reference Skill** (não de disciplina). `writing-skills` dispensa micro-test de wording para skills puramente de referência ("N/A for pure reference skills") e define o teste como **retrieval + application**. A "baseline" já é conhecida do mapeamento: sem a skill, um agente (a) não sabe qual das 10 tools usar para cada intenção, (b) confunde `b24hub_search` (BM25) com `b24hub_grep` (substring), (c) chama `b24_call` sem ler a doc antes, (d) tropeça nas 9 armadilhas. **Verificação proposta pós-criação** (fora do plan mode): rodar 2-3 cenários de aplicação com subagent fresh-context ("projetar um processo SPA", "como reagir a OnCrmLeadAdd", "exemplo de batch em Python") e confirmar que o agente escolhe as tools certas e na ordem certa.
